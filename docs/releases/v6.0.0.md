# ChatISA v6.0.0 Release Notes

**Release Date:** July 26, 2026

---

## Overview

Version 6.0.0 replaces the Streamlit application with a full-stack Next.js
platform. This is a rewrite rather than an upgrade: the interface, the
authentication model, the data layer, the deployment, and the testing strategy
are all new. The Python application is preserved under `legacy/` and remains
readable, but it is no longer what runs.

Three things changed that a student notices immediately:

- **Sign-in.** Access is restricted to verified `@miamioh.edu` Google accounts,
  so the app no longer runs open to the internet.
- **Code runs in the browser.** Python, R, and SQL execute in the student's own
  tab through WebAssembly. Their code and data never reach our server.
- **Eight modules, not six.** Coding Companion split into a tutor and a
  workbench, and Ask Anything and JobApp Drafter are new.

Two things a maintainer notices:

- **Secrets are server-side.** The legacy app embedded an OpenAI client secret
  in page HTML and in an iframe URL fragment. Nothing reaches the browser now.
- **There are tests.** 735 unit tests and 17 end-to-end suites, from a starting
  point of none.

## Architecture

- **Next.js 16 (App Router) + TypeScript + React 19**, served over HTTPS by a
  custom launcher on the existing Windows Server.
- **Vercel AI SDK** provider registry; all provider calls server-side, streamed
  with cancellation.
- **Auth.js v5** Google OAuth restricted to verified `@miamioh.edu`, with two
  independent guard layers.
- **SQLite (Drizzle + better-sqlite3)** for users, usage analytics, exams,
  interviews, applications, and projects.
- **WebAssembly runtimes**, self-hosted: Pyodide (Python), WebR (R), and SQLite
  WASM, plus a mirrored R package repository so the common packages install from
  our own origin rather than a third-party CDN.
- **Tailwind v4** with Miami design tokens; WCAG 2.1 AA, verified by automated
  axe scans at desktop and 320px widths.

### Privacy

- **Chat content is never persisted** (ADR-022). The `conversations` and
  `messages` tables were removed; only content-free usage events are stored.
- **Uploaded documents are never persisted** (ADR-015). Exam Prep stores sampled
  excerpts, not the file.
- **Code and data stay in the browser** for the Coding Studio and for Ask
  Anything's `run_python` / `run_r` / `run_sql`.

## Notable engineering

Full rationale for each of these is in `docs/development/decision-log.md`
(24 ADRs) and the dated design documents beside it.

- **Cross-origin isolation** on every page that can execute code. Without a
  `SharedArrayBuffer`, WebR silently loses all networking, and the failure
  surfaces as an unrelated R error (ADR-023).
- **A Run button is only offered when the code can actually run.** Package
  requirements are parsed from the snippet and classified against Pyodide's lock
  and a generated WebR availability manifest; a package that cannot exist in the
  browser gets an explanation instead of a button that can only fail (ADR-024).
- **House chart style**, shared by the Coding Tutor, the Coding Studio chat, and
  Ask Anything. Every palette hex was checked with a colour-vision validator
  rather than chosen by eye, and the contract escalates from the Miami palette to
  ColorBrewer Dark2 to "do not colour this at all" as the series count grows.
- **A deploy bundle that verifies itself.** The bundler refuses to ship a bundle
  containing a symlink, an unmaterialized package, development data, or one that
  fails a real boot with a deep health check.
- **A live-model test harness** (`npm run test:live`), separate from the
  deterministic suite, that drives real models through the real UI and records
  every tool call, console error, and failed request.

## Testing

| Suite | Count | What it covers |
| --- | --- | --- |
| Unit (Vitest) | 735 tests, 76 files | Pure logic, prompt contracts, guards |
| End-to-end (Playwright) | 17 specs, desktop + 320px | The app against a deterministic mock model |
| Live (opt-in) | 6 specs | Real models, real providers, real artifacts |

The end-to-end suite runs with `CHATISA_MOCK_LLM=1`, so it calls no provider and
spends no sponsored budget. The live suite is opt-in and refuses to run against a
mock server, because a live suite pointed at one produces confident, meaningless
passes.

Included in the unit suite are 50 characterization tests that pin the new
TypeScript against the legacy Python's behaviour, so the port can be shown to
match rather than asserted to.

## Upgrading from v5.x

There is no in-place upgrade path; this is a different application.

1. Build the bundle on a development machine:
   `node scripts/make-deploy-bundle.mjs`
2. Copy `deploy/chatisa-app.zip` to the server and extract it with 7-Zip.
3. Fill in `chatisa.env` from `chatisa.env.example`. `AUTH_URL`, `AUTH_SECRET`,
   the Google OAuth pair, and `CHATISA_DATA_DIR` are required; provider keys are
   required for the modules to answer.
4. Point Task Scheduler at `chatisa.bat`.

Full instructions ship with the bundle in `INSTALL.txt`, and the operational
detail is in `docs/operations.md`.

**Analytics start clean** (ADR-006): the legacy JSONL activity log is not
migrated.

**The legacy app still runs.** `legacy/` holds the Streamlit application
unchanged, for reference and for anyone reproducing the prior behaviour.

## How this was built

The transition from Streamlit to this platform was carried out with **extensive
use of Claude Code**, working under a staged workflow: understand, plan, then
implement only on explicit approval, with a stop for review after each slice.

That shows up in the repository in ways worth knowing about if you are reading
the history or the docs:

- **The design record is unusually complete.** `docs/development/` holds 36 dated
  design and plan documents, a 24-entry decision log, an interaction log, and a
  migration log, because each slice was specified and reviewed before it was
  written. `docs/development/2026-07-26-hardening.md` is a worked example: seven
  production defects, each with the evidence that found it.
- **Verification was the constraint, not code volume.** The rule throughout was
  never to claim an unexecuted test. Several findings in the hardening pass were
  corrections of earlier wrong conclusions, and those corrections are recorded
  next to the conclusions rather than quietly replacing them.
- **The tests exist because the port had to be provable.** The 50
  characterization tests pin the TypeScript against the legacy Python's actual
  behaviour, so parity is demonstrated rather than asserted.

The engineering decisions, the model roster, the pedagogy, and every scope call
remained the maintainers'.

## Known limitations

Stated plainly rather than discovered later.

- **Exam Prep ingest scales superlinearly.** A 12-slide deck is ready in about
  11 seconds; a 37-slide deck was still not ready at 431 seconds. Large uploads
  need chunked or background ingest.
- **The browser proxy caps responses at 25 MB.** Enough for most public
  datasets, but a large archive must be attached instead of fetched.
- **The hosted provider sandboxes have no network.** They build files; they
  cannot download data.
- **`statsforecast`, `pyreadr`, and anything needing a native toolchain cannot
  install** in the browser runtimes. The app now says so instead of offering a
  Run button.
- **Generated decks keep one of the template's nine layouts.** They open
  correctly and carry the Miami theme.
