# ChatISA v6.4.0 Release Notes

**Release Date:** August 21, 2026

---

## Overview

Publishing student work moves out of Job Scout and becomes its own module.
**Portfolio Builder** (`/portfolio`, listed first under "For your job
search") turns a student's material into a self-contained GitHub Pages site
in one of two shapes, and shows them the page before it goes anywhere. The
Portfolio Site tab and the "Polish a project I already built" pane leave Job
Scout, which goes back to being about jobs, the profile, and scaffolds.

Design spec: `docs/superpowers/specs/2026-08-20-portfolio-builder-design.md`
(ADR-028).

## Portfolio Builder

Two modes, chosen on the first step:

| | Career portfolio | Project showcase |
|---|---|---|
| Question it answers | "Who I am and what I can do" | "One project, told as a story" |
| Inputs | resume PDF, classes taken, one to five projects, optional photo, name and links | one course, semester, optional team names, and the project's files: data, code or notebooks, report, slides, figures |
| Page | hero, about, skills, projects, courses, experience, education, contact | problem, data, approach, findings with figures, deliverables, team |
| Repository | `portfolio`, one per student, republished in place | `<course>-<title>`, for example `isa-401-churn-model`, one per project |

Both modes share the same spine: intake in the browser, one model call that
emits content JSON only, a deterministic escaping template that renders the
HTML, a preview the student edits, and a push straight from their browser to
their own GitHub account.

**The review step is the point of the module.** The generated page appears in
a sandboxed preview iframe beside a field-by-field editor: every heading,
paragraph, bullet, project blurb and finding is editable, list items reorder
and delete, and the preview re-renders on each keystroke. Nothing is
published until the student presses Publish, and republishing a site updates
the same repository rather than creating a second one. Published sites are
listed on the first step with "Update" and "View". There is no per-section
"regenerate" button: a wrong sentence is faster to fix by typing over it,
and stepping back to change the inputs regenerates the whole page.

**Everything stays on the device.** Site records (what exists, where it is
published) live in localStorage; drafts, files, the photo and the generated
HTML live in IndexedDB, one record per site. The server reads uploads
transiently to write the page and keeps none of them. The only server records
are the existing content-free usage events (`portfolio_generated`,
`portfolio_published`, with the site kind).

**What is published, and what is not.**

- Data files start unpublished, with a reminder that course datasets are
  often licensed or instructor-provided and a per-file checkbox to include
  one deliberately. Code, notebooks, reports, slides and figures start
  included.
- The photo is resized in the browser to 512 px on the long side and
  re-encoded as a JPEG under 150 KB, which also strips EXIF, so a phone
  photo's location data cannot reach a public repository.
- The resume PDF is source material by default. It is published only when
  the student ticks "Include a resume download link", which says plainly
  that the PDF becomes public including any phone number or address on it.
- The push engine's limits (60 files, 400 KB per file, 2 MB in total) are
  shown as a running size meter and enforced **before** generation, naming
  the files that are over, rather than failing at the push after the model
  has already been paid for.

**New routes.** `POST /api/portfolio/generate` serves both modes: `auth()`,
rate limit, model gating through `PAGE_MODELS.portfolio` (structured output,
64k context), zod input, `generateObject`, `recordUsageEvent`. Everything the
model returns is validated against the material a second time on the server:
career projects are filtered to the slugs actually submitted, a showcase
finding's `figure` must be one of the figures being published or it becomes
null, deliverables must point at published paths, and skills must resolve to
taxonomy ids. `POST /api/portfolio/event` is a publish beacon and carries the
site kind only, because the push itself happens in the browser where the
server cannot see it.

**Binary files now push.** `lib/scout/github.ts` gained a base64 encoding on
`PushFile`: those files are uploaded as blobs first and referenced by sha in
the tree, so photos, resume PDFs, figures, notebooks and Office documents
survive a push intact. Size accounting decodes base64 rather than measuring
the encoded string.

## Job Scout

- The **Portfolio Site tab is gone** and so is the **Polish a project I
  already built** pane. Both capabilities live in the Portfolio Builder now,
  and each tab that lost something carries a link card to the mode that
  replaced it. Job Scout keeps four tabs: Profile, My Projects, This Week's
  Jobs, Saved Jobs.
- `/job-scout?tab=portfolio` and `/job-scout/github-connected` redirect to
  the new module, and the GitHub connect landing page is module-neutral at
  `/portfolio/github-connected`, so saved links and mid-flight OAuth
  connections still land somewhere sensible.
- **Published sites count toward the profile.** The skills on a published
  site, career or showcase, feed skill matching exactly as a built project's
  do, because the repository exists and the work is real.
- A project polished under v6.3.0 keeps its record and its skills, and its
  GitHub link still works, but it can no longer be re-pushed: the stored
  polish plan has no scaffold shape and the pane that produced it is gone.
  Rebuilding it as a showcase is the path forward.

## JobApp Drafter

A per-draft **"Include my published work"** toggle, off by default. When it
is on, the browser sends the titles, one-line summaries, skills and URLs of
the student's published sites along with the application, so the resume can
carry a line with real links and the cover letter can cite something the
reader is able to open. Nothing new is stored: the block rides along with the
resume text the route already keeps, and it is placed first so a long resume
cannot push it past the fence in `lib/documents/generate.ts`.

## Fixes

- **GitHub connect failed in production** with "redirect_uri is not
  associated with this application". The OAuth redirect was built from the
  incoming request's origin, which behind the TLS relay is the internal
  `127.0.0.1:3000` address rather than the public host the OAuth app was
  registered against. It is now built from `AUTH_URL` via a new
  `publicOrigin()` helper, with the relay's `x-forwarded-*` headers as a
  fallback and the raw request origin only for plain local development.
- **Zip downloads and the command-line instructions are gone** from Job
  Scout's projects. GitHub is the only destination, and offering a second
  half-supported path was its own source of confusion.

## Operator notes

- **No new required environment variables.** The GitHub OAuth pair from
  v6.3.0 is what powers publishing; absent it, the Connect, Push and Publish
  buttons stay hidden.
- The GitHub OAuth App's Authorization callback URL is unchanged:
  `https://chatisa.fsb.miamioh.edu/api/scout/github/callback`. Both env
  examples now record that the callback is built from `AUTH_URL`, so
  `AUTH_URL` must be the public https origin.
- `CHATISA_PORTFOLIO_LIMIT_PER_MINUTE` (default 4) is optional and exists for
  the same reason as `CHATISA_SCOUT_PROJECT_LIMIT_PER_MINUTE`: the parallel
  e2e projects generate several sites a minute from one shared account.
  Production behavior is unchanged when it is unset.
- The **GitHub Pages API caveat is unchanged**: enabling Pages through the
  API can need broader scope than `public_repo` on some accounts, so a failed
  enable still falls back to a one-click link to the repository's Pages
  settings.

## Test and gate results

- 96 unit test files, 895 tests, all passing (37.8s). New coverage: the
  content schemas and the v1 to v2 migration, file roles and repository
  layout, both renderers (escaping, `safeHref`, fixed image paths, figure and
  deliverable validation), the photo resize, the site and published-work
  stores, the intake path, the publish plan, the generate route under
  `CHATISA_MOCK_LLM=1` for both modes, base64 push accounting, and
  `safeReturnPath`'s new default.
- `tests/e2e/portfolio.spec.ts` plus `tests/e2e/job-scout.spec.ts`: 27 passed
  across desktop and mobile-320. The portfolio spec drives both wizards end to
  end against an intercepted fake api.github.com, asserts the exact pushed
  file tree (including that an unticked dataset and a resume PDF whose
  download link was left off are both absent), checks that a published
  showcase then appears in Job Scout's profile and in JobApp Drafter's
  toggle, scans the mode step and the review
  step with axe (zero violations), and asserts the unauthenticated redirect
  and 401s. No test traffic reaches real GitHub or a real model.
- Typecheck and lint clean; the deploy bundle builds and passes its boot and
  deep-health self-test.
- **Known failures, not fixed by this release.** A full Playwright run on the
  build machine reported 271 passed, 30 failed, 24 skipped. None are in the
  portfolio or Job Scout specs. Rerun in isolation, the reproducible ones are:
  `project-assistant.spec.ts`, `project-assistant-session.spec.ts` and
  `project-team.spec.ts` (axe evaluate timeouts and a coach page that never
  finishes navigating, in the module the team knows is still in flux);
  `shell.spec.ts`'s deep-health test, which asserts an exact list of deep
  check keys and predates the `scout` key the health route has returned since
  v6.1.0; `sandbox.spec.ts`'s statsforecast fit; and Ask Anything's hosted
  deck generation. The rest were load flakes that passed on rerun. These are
  pre-existing and belong to their own modules; this release does not claim
  to have fixed any of them.
